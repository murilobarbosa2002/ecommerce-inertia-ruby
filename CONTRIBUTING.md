# Contribuindo

Obrigado pelo interesse em contribuir com este template open source de e-commerce. Este documento descreve o processo esperado.

## Antes de abrir um PR

1. Leia o [`README.md`](README.md) para entender o que é o projeto, e os ADRs em [`docs/adr/`](docs/adr/) para as decisões de arquitetura já fixadas e seus porquês.
2. Leia a seção "Padrões de código" abaixo — todo código novo precisa seguir Clean Code, Clean Architecture e SOLID como baseline, não como aspiração (ver `docs/adr/0004-clean-architecture-solid-as-baseline.md`).
3. Para mudanças com impacto arquitetural (nova dependência estrutural, mudança de como camadas se relacionam, etc.), proponha ou já inclua um ADR em `docs/adr/` explicando o porquê — veja `docs/adr/0001-record-architecture-decisions.md`.
4. Abra uma issue descrevendo o problema/proposta antes de começar um trabalho grande, para alinhar escopo e abordagem.

## Reportando bugs

Abra uma issue com: passos para reproduzir, comportamento esperado vs. observado, e ambiente (versão de Ruby/Node, navegador, se relevante). Para vulnerabilidades de segurança, **não** abra uma issue pública — veja [`SECURITY.md`](SECURITY.md).

## Padrões de código

Este projeto segue **Clean Code**, **Clean Architecture** e **SOLID** como baseline obrigatório, não como aspiração (ver `docs/adr/0004-clean-architecture-solid-as-baseline.md`):

- **Regra de negócio não mora em controller nem em callback de ActiveRecord.** Controllers orquestram (recebem request, chamam um service/use case, respondem); regra de negócio vive em objetos de domínio/service objects testáveis isoladamente.
- **Isolamento nicho ↔ core.** Qualquer coisa específica de um negócio (textos, flags de quais páginas existem, tema visual, SEO) deve ser **configuração**, injetada no domínio core, nunca o inverso — isso inclui qualquer PR que acople o core a um caso de uso de nicho específico.
- **Dependências apontam para dentro.** Camadas de infraestrutura (banco, gateways de pagamento, envio de e-mail) implementam interfaces que o domínio define — o domínio não conhece detalhes de implementação externa.
- **Sem fat controllers, sem callback soup, sem God objects.** Classes pequenas, com uma responsabilidade clara (SRP). Prefira composição a herança profunda.
- **Nomes sempre completos e descritivos, nunca abreviados ou ambíguos.** Proibido nomear variável/parâmetro/método com letra solta ou abreviação (`e`, `a`, `t`, `tmp`, `obj`, `val`, `arr`, `str`...), mesmo em blocos curtos, lambdas ou loops. O nome precisa deixar óbvio o que a coisa é/faz (ex. `digital_product`, não `prod`/`dp`; `calculate_total_price`, não `calc_total`/`ct`).
- **URL pública de ação de "entrada" (login, verificação de código) nunca usa o `/new` que `resource`/`resources` gera por padrão** — não faz sentido pro usuário final (`/admin/login/new` em vez de `/admin/login`). Use rotas customizadas (`get "login", to: "sessions#new", as: :new_admin_session`) em vez de `resource :session, only: %i[new create destroy]`. **Dentro de `namespace`, `as:` explícito prefixa "admin_" antes do nome dado** (`as: :new_session` vira `admin_new_session`, não `new_admin_session` como o `resource` original gerava) — bug real já encontrado. Pra manter o nome de helper exato que um `resource` geraria, use `scope path: "admin", module: "admin_panel" do ... end` em vez de `namespace`, escrevendo o nome final direto em `as:`.
- **Namespace de controller/service não pode ter o mesmo nome de uma classe já existente.** Ruby não permite reabrir uma classe (`class Admin < ApplicationRecord`) como módulo de namespace (`module Admin; class SessionsController; end; end` levanta `TypeError: Admin is not a module`) — erro só aparece rodando o código, não lendo a definição isoladamente. Antes de nomear uma pasta de controller/service/concern igual a um model existente, confirme que o nome não colide; se colidir, use `namespace :rota, module: "nome_alternativo"` no `routes.rb` pra manter a URL/route helper como estavam, só trocando a classe Ruby (ex. `AdminPanel::` em vez de `Admin::` pros controllers do painel, já que o model `Admin` ocupa esse nome).
- **Sem string/valor mágico espalhado pelo código.** Nada de comparar ou atribuir strings/números literais soltos (ex. `status == "pago"`, `role = "admin"`) em múltiplos lugares. Use enums (`enum` do ActiveRecord quando fizer sentido no domínio) ou constantes/módulos de constantes nomeados, definidos uma vez, referenciados em todo lugar.
  - **Exceção deliberada: valor esperado de uma mensagem traduzida (I18n), em teste que existe justamente pra verificar que a tradução está correta.** Nesse caso, a string literal (ex. `expect(flash[:alert]).to eq("E-mail ou senha inválidos")`) *é* a asserção — trocar por `I18n.t("a.mesma.chave")` faz o teste comparar a chave contra ela mesma (`I18n.t(chave) == I18n.t(chave)`), sempre verdadeiro mesmo com a tradução quebrada/faltando, e o teste some de ter valor nenhum. Confirmado quebrando a tradução de propósito: a versão com `I18n.t(...)` continuou verde; a versão com string literal foi pro vermelho, como devia. Regra então é: dado de teste arbitrário (senha, nome, etc.) repetido em vários lugares vira constante; texto esperado de uma tradução sob teste fica literal.
- **Cada `event_type` de `AuditEvent` representa exatamente um fato, nunca reaproveitado entre contextos diferentes.** Achado real durante a implementação do 2FA (`docs/adr/0013`): `login_failed` estava sendo usado tanto pra senha errada na tela de login quanto pra reautenticação errada ao desativar o 2FA — dois audit trails diferentes misturados sob o mesmo rótulo, impossível de distinguir depois só pelo log. Da mesma forma, `login_succeeded` chegou a disparar só com a senha certa, mesmo quando a conta tinha 2FA pendente e nenhuma sessão de verdade havia sido criada ainda — um log enganoso, parecendo login completo sem ter completado. Ao adicionar um novo ponto de auditoria, pergunte "esse evento já existe pra outra situação, ou é um fato novo?" antes de reusar um `event_type` existente — na dúvida, crie um valor novo no enum (`app/models/audit_event.rb`) em vez de generalizar um que já tem um significado mais específico.
- **PaperTrail (`docs/adr/0013`) só rastreia campo editorial, nunca campo de estado operacional/automático.** Ao adicionar `tracked_by_change_reason` (concern `app/models/concerns/change_reason_required.rb`) a um model, liste só os atributos que um admin edita deliberadamente (ex. `email_address`) — nunca um atributo que um service interno atualiza como parte do fluxo normal (ex. `failed_login_attempts`, `locked_at`, `otp_secret`), porque esse já é coberto pelo `AuditEvent` (evento de negócio) e não tem um "motivo" humano pra pedir. Achado real implementando isso no `Admin`: listar todos os atributos quebrou ~35 specs de serviços internos que fazem `update!` sem `change_reason`. `tracked_by_change_reason` usa a opção `only:` do PaperTrail e condiciona a validação de presença a `if: -> { atributo_rastreado_changed? }`, então um update que não toca nenhum atributo listado nem cria versão nem exige `change_reason`. **A validação em `create` e o `before_destroy` são incondicionais, não só a de `update`** — adicionar `tracked_by_change_reason` a um model novo (não só editar um já existente) quebra toda `factory` do FactoryBot e todo seed/spec que cria ou destrói esse model sem `change_reason` (achado real fazendo isso no `Role`: `spec/factories/roles.rb` e `db/seeds.rb` precisaram de `change_reason` que não existia antes, e um spec que fazia `role.destroy!` direto também). **A mensagem de erro de `change_reason`/qualquer atributo rastreado depende de tradução própria por model** — `config/locales/pt-BR.yml` só tem `activerecord.attributes.<model>.<atributo>` traduzido model a model; sem a entrada do model novo, o Rails humaniza o nome em inglês (`"Change reason não pode ficar em branco"`, mistura de idioma) em vez de usar a tradução. Adicione a entrada em `activerecord.attributes.<model>` junto com `tracked_by_change_reason`, não depois.
  - **PaperTrail serializa `object`/`object_changes` em YAML, e Rails >= 7 carrega essas colunas com `YAML.safe_load`** — sem configurar `ActiveRecord.yaml_column_permitted_classes` (`config/initializers/paper_trail.rb`, lista recomendada pela própria documentação do PaperTrail), `reify`/`previous_version` falha com `Psych::DisallowedClass` pra qualquer atributo `datetime` (vira `ActiveSupport::TimeWithZone`) — bug real encontrado escrevendo o spec de reverter uma versão.
  - **`has_many :through` com `has_paper_trail` no model de junção precisa de `dependent: :destroy` na associação `through`, não só na `has_many` de baixo nível.** Remover um item de uma coleção `through` (`papel.permission_ids = [...]`, `papel.permissions = [...]`) sem isso usa `scope.delete_all` do Rails — um `DELETE` em lote direto no banco que nunca passa por callback nenhum (nem `after_destroy`, nem o do PaperTrail) — então revogar um item não deixava rastro de auditoria nenhum, enquanto conceder gerava versão normalmente. `has_many :permissions, through: :role_permissions, dependent: :destroy` (não só `has_many :role_permissions, dependent: :destroy`) faz o Rails chamar `.destroy` em cada registro removido, com callback. Pra gravar o `change_reason` do pai na versão do model de junção sem duplicar o atributo, `record.belongs_to_pai.change_reason` dentro do `meta:` funciona de verdade — o Rails resolve a associação `belongs_to` pro mesmo objeto em memória que está sendo manipulado (`inverse_of` automático), não uma cópia recarregada do banco sem o atributo virtual. Bug real encontrado investigando a cobertura de auditoria do RBAC (`Role`/`RolePermission`) antes do primeiro commit da feature — ver `docs/bugs/audit-logging.md`.
  - **Anexar um arquivo a um `has_one_attached`/`has_many_attached` num registro já persistido aciona um `touch` nele (`belongs_to :record, touch: ActiveStorage.touch_attachment_records` em `ActiveStorage::Attachment`, `true` por padrão) — isso ainda cria uma versão "update" no PaperTrail mesmo que o attachment não seja um atributo de `tracked_by_change_reason`.** Essa versão não carrega `object_changes` (nenhuma coluna real mudou), mas carrega `change_reason`/`whodunnit` normalmente (o `meta:` é sempre mesclado, inclusive em evento de `touch`). Não assuma "attachment não é coluna rastreada" ⇒ "nenhuma versão é criada" — são coisas diferentes: achado real escrevendo o spec de `StoreSetting#logo`, onde uma asserção inicial de "nenhuma versão nova" dava falso vermelho porque o `touch` automático criava uma versão vazia mesmo assim.
- **Comentário só como documentação formal de API, nunca como muleta de nome ruim.** Se o código precisa de um comentário explicando "o quê" ou um "por quê" óbvio, o nome está errado — renomeie em vez de comentar. Comentários são aceitáveis como **YARD** (equivalente Ruby ao PHPDoc/JSDoc) documentando contrato público de classes/métodos, ou para explicar um "porquê" não óbvio (ex. um workaround, uma decisão não trivial).
- **Pendência marcada no código usa uma das três tags rastreadas pela extensão `gruntfuggly.todo-tree`** (configuração em `.vscode/settings.json`, instalação documentada em `docs/environment-setup.md`): `TODO:` pra trabalho futuro genérico, sem bloqueio (ex. uma PR planejada que ainda não chegou); `FIXME:` pra lacuna/gap conhecido que precisa de correção (não é só "fazer depois", é "tem algo incompleto/errado aqui"); `PENDING-FRONTEND:` especificamente pra algo que só é resolvível quando a página/tela correspondente do painel existir (backend pronto, mas sem como verificar/usar de ponta a ponta ainda). Toda tag inclui uma frase curta explicando o motivo e, quando fizer sentido, uma referência ao ADR/issue relevante — nunca só a palavra sozinha.
- Backend Ruby: siga as regras do Rubocop configuradas no projeto (`bundle exec rubocop`).
- Frontend: TypeScript, componentes React pequenos e testáveis. Siga ESLint (`pnpm lint`) e Prettier (`pnpm format:check`) configurados no projeto — `eslint.config.mjs` inclui regras de tipagem estrita (typescript-eslint `strictTypeChecked`), React, acessibilidade (`jsx-a11y` strict) e Tailwind; Prettier (com `prettier-plugin-tailwindcss`) é quem formata/ordena classes, não o ESLint.
- **Formulário sempre com Zod + `zodResolver` + React Hook Form**, nunca validação manual ad-hoc. **Componente de UI com comportamento (modal, select, checkbox, etc.) sempre parte de um primitivo do pacote `radix-ui`**, estilizado por este projeto com Tailwind — nunca reimplementado do zero. **Variante de estilo usa `tv()` do `tailwind-variants`**, não concatenação manual de classe condicional. Racional completo em `docs/adr/0012-form-validation-and-ui-primitives-stack.md`.
  - **Todo campo de formulário bindado a um componente Radix controlado (`Select`, etc.) via `Controller` precisa de valor inicial definido em `defaultValues` do `useForm()`** — mesmo sendo string vazia, nunca `undefined`. Sem isso, o componente nasce "uncontrolled" e vira "controlled" assim que o primeiro valor real é escolhido, gerando o aviso real do React de componente trocando de modo no meio da vida (gotcha real encontrado integrando `Select` com RHF no formulário de admins).
- **Nunca usar o tipo `any`.** Toda variável, parâmetro, retorno de função e prop de componente precisa de um tipo real. Se o tipo correto não for óbvio, pesquise (documentação oficial da lib, Context7) em vez de recorrer a `any` ou `as any` como atalho. `unknown` + narrowing é aceitável quando o tipo genuinamente não pode ser conhecido antecipadamente (ex. parsing de JSON externo) — `any` nunca é.
- **HTML sempre semântico.** Use o elemento certo pro que ele representa (`header`, `nav`, `main`, `section`, `article`, `footer`, `button`, `label`, etc.) em vez de `div`/`span` genérico quando existe elemento semântico apropriado — acessibilidade e SEO dependem disso, e SEO é uma feature explícita do painel admin deste projeto.
- **Acessibilidade é baseline obrigatório, não aspiração** (`docs/adr/0028`). `eslint-plugin-jsx-a11y` (`strict`) já pega defeito sintático (label sem associação, `aria-*` inválido) — não é suficiente sozinho, revisão manual é esperada em todo componente/página nova pelo que o lint não cobre:
  - `<html>` sempre com `lang` (`app/views/layouts/application.html.erb`, lido de `I18n.locale`, nunca hardcoded).
  - Conteúdo dinâmico relevante (erro, aviso) usa `role="status"`/`role="alert"` (ou `aria-live` equivalente) — nunca só uma mudança visual sem anúncio pra leitor de tela.
  - Diálogo/modal sempre associa descrição via `RadixDialog.Description` (nunca um `<p>` solto) — sem isso o Radix não monta `aria-describedby`.
  - Contraste de cor **calculado** (fórmula de luminância relativa do WCAG), nunca estimado visualmente — mínimo 4.5:1 pra texto normal, 3:1 pra indicador de estado de UI (WCAG 1.4.11, ex. borda de campo inválido). Achado real: `border-red-300`/`dark:border-red-700` do `Input` davam 1.90:1/2.27:1, abaixo do mínimo — corrigidas pra `border-red-500`/`dark:border-red-500` (`docs/bugs/accessibility.md`).
  - Grupo de controle relacionado (checkboxes, radios) sempre em `fieldset`/`legend`, nunca solto numa `div`.
- **Em caso de dúvida sobre como uma biblioteca/framework/API funciona, consulte a documentação oficial atual antes de implementar** — não assuma pelo que "parece familiar" de outra versão ou outra lib.
- **Mensagem de flash do Inertia é lida via `usePage().flash`, nunca `usePage().props.flash`.** `flash` é um campo próprio do objeto de página (`{ component, props, flash, ... }`), paralelo a `props`, não aninhado dentro dele — bug real encontrado testando no browser (`usePage().props.flash` sempre retornava `undefined`, quebrando a página inteira). Só existe de fato quando há `notice:`/`alert:` pra mostrar; trate como opcional (`flash?.notice`), mesmo o tipo de `@inertiajs/core` declarando como sempre presente.
  - **Todo layout de página (`AuthLayout`, `PanelLayout`, qualquer um novo) renderiza `Banner` a partir de `usePage().flash` desde a criação** — nunca como retrofit depois que uma página já precisa mostrar erro/sucesso. Controller sinaliza falha de validação via `redirect_to ..., alert: ...` (mensagem localizada, ex. `admin.errors.full_messages.to_sentence`), nunca via `inertia: { errors: ... }` (protocolo de erro por campo do Inertia) — nenhum componente deste projeto consome `usePage().props.errors`/chama `setError` do React Hook Form com ele; gotcha real encontrado implementando `AdminsController`, onde os dois problemas (controller usando um protocolo sem consumidor, `PanelLayout` sem `Banner` nenhum) deixavam qualquer mensagem de erro/sucesso invisível.
- **Fonte do projeto é Inter, self-hosted via `@fontsource-variable/inter`** (`app/frontend/entrypoints/application.css`, `--font-sans` do `@theme`) — nunca depender só do stack padrão de fontes do sistema operacional (`-apple-system`, `Segoe UI`, etc.). Bug real encontrado testando no browser: sem nenhuma dessas fontes instalada na máquina, o fallback do Chromium renderizava espaçamento entre palavras visivelmente quebrado, sem nenhuma propriedade CSS indicando a causa.
- **Todo texto novo visível a humano passa por chave de I18n (`I18n.t`/`t`), nunca string literal direto no código** — formulário, e-mail, mensagem de erro, página, prompt de CLI. Única exceção: texto de debug/log interno nunca visto por humano fora de desenvolvimento. Locale padrão é `pt-BR` (`docs/adr/0014-i18n-default-locale-and-content-separation.md`). Conteúdo real de produto (model, formulário, e-mail, página) vai em `config/locales/pt-BR.yml`; texto de ferramenta interna de linha de comando (rake task) vai em `config/locales/cli.pt-BR.yml` — nunca misturados no mesmo arquivo.
  - **No frontend, I18n é via `i18next`/`react-i18next`** (`app/frontend/i18n.ts`, recursos em `app/frontend/locales/pt-BR.ts`, único locale, sem backend assíncrono) — mesmo racional do backend, só que não existe equivalente de `I18n.t`/`t` nativo em React. Chave de tradução sempre como **string literal** (`t("admin.session.new.title")`), nunca a sintaxe de seletor `t($ => $.admin.session.new.title)` dos exemplos oficiais do react-i18next — essa sintaxe não type-checka com a versão/configuração deste projeto (erro `Parameter '$' implicitly has an 'any' type`), apesar de ambas as formas serem igualmente verificadas em compile-time contra as chaves reais via `app/frontend/types/i18next.d.ts` (module augmentation de `CustomTypeOptions.resources`).
  - **A gem `rails-i18n` não cobre 100% das mensagens que o Rails gera** — bug real encontrado: `has_secure_password` usa a chave `password_too_long` (fora do namespace `activerecord`, para a senha de até 72 bytes aceita pelo bcrypt) e `rails-i18n` não traduz essa chave específica pra `pt-BR`, aparecendo como `"Translation missing"` pro usuário. Toda vez que um model novo usar `has_secure_password` (ou qualquer feature do Rails que gere mensagem de validação), **teste de verdade a mensagem de erro renderizada** (não assuma que `rails-i18n` cobre) e adicione a chave em `config/locales/pt-BR.yml` se faltar (`errors.messages.<chave>` pra mensagem genérica, `activerecord.attributes.<model>.<atributo>` pro nome do campo).
- **URL/ação de formulário no frontend nunca é string hardcoded** (`href="/admin/login"`, `router.post("/admin/login", data)`) — use os helpers tipados gerados por `js-routes` a partir de `config/routes.rb`, importados de `@/routes` (ex. `admin_session_path()`, `new_admin_password_path()`), mesmo nome do helper Ruby correspondente (`docs/adr/0018-js-routes-typed-path-helpers.md`). Rota renomeada/removida quebra em compile-time (`pnpm check`) em todo call site, não em runtime no browser — bug real quase causado no PR das primeiras páginas de autenticação, só pego por revisão manual. `app/frontend/routes.js`/`routes.d.ts` são gerados (gitignorados, fora do escopo do ESLint), nunca editados à mão.
- **Hierarquia fixa de componente/arquivo no frontend** (`docs/adr/0019-frontend-component-hierarchy-and-file-organization.md`):
  - **Primitivo de UI reutilizável** (usado por mais de uma página) vira componente em `components/shared/<nome-do-componente>/` (kebab-case, uma pasta por componente — nunca agrupado por categoria genérica como `form/`), com três arquivos de responsabilidade única dentro: `<Nome>.types.ts` (tipo/`interface` de prop), `<Nome>.variants.ts` (variante `tv()`), `<Nome>.tsx` (só o JSX do componente, importando os outros dois). Um primitivo nunca fica aninhado dentro da pasta de outro só por coincidência de uso atual (ex. `label/`/`field-error/` não ficam dentro de `input/` mesmo só aparecendo ao lado de `Input` até agora) — a pasta reflete se o componente é genérico por natureza, não quantos lugares o usam hoje. **Exceção justificada: ícone SVG estático vive em `components/shared/icons/<nome-do-ícone>/`** (`docs/adr/0027`) — diferente de `form/` (papéis diferentes agrupados por coincidência), ícone é genuinamente a mesma categoria de coisa (SVG estático sem variante nem prop própria), já reconhecida como tal na exceção de "sem variante/sem prop" deste mesmo ADR.
  - **Componente específico de uma página** (não reutilizável fora dela, ex. o `<form>` inteiro de uma tela) vive em `pages/<Segmento>/components/<Página>Form.tsx` — pasta `components/` local ao segmento, nunca confundida com `components/shared/` (genérico) ou `components/admin/` (variante de estilo sem componente próprio ainda).
  - **Arquivo da página (`New.tsx`, `Edit.tsx`) só compõe o layout** — `useTranslation`, `<AuthLayout>`/`<Head>`, e o(s) componente(s) filho(s). Nenhum `useForm`, schema, `<form>` inteiro ou `router.post`/`router.patch` direto nesse arquivo. **Isso vale pra qualquer hook/lógica de interação, não só formulário** (`docs/adr/0025`) — uma ação com `usePage()`, condição de permissão ou efeito colateral (ex. confirmar e enviar uma requisição) vira seu próprio componente em `components/`, nunca inline na página. Achado real: o botão "Resetar 2FA" (`Admin/Admins/Edit.tsx`, #54) nasceu direto na página, chamando `usePage()` e resolvendo a lógica de confirmação ali mesmo — corrigido extraindo pra `components/ResetTwoFactorButton.tsx`.
  - **Schema, hook e componente de formulário, cada um no seu arquivo**: `<Página>.schema.ts` (Zod + tipo derivado), `use<Página>Form.ts` (encapsula `useForm`/`zodResolver`/submissão, ao lado do arquivo da página, fora de `components/` — é lógica, não apresentação) e `pages/<Segmento>/components/<Página>Form.tsx` (o JSX do formulário, chamando o hook).
  - **Tipo da entidade recebida como prop do backend (distinto do tipo derivado do schema Zod) sempre em arquivo próprio, nunca inline/duplicado entre página/hook/componente** (`docs/adr/0025`): usado só por uma página → `<Página>.types.ts`, sempre com o formato **completo** das props da página (não só a entidade — form component que recebe exatamente o mesmo formato reusa o mesmo tipo, nunca redeclara); usado por mais de uma página do mesmo segmento (ex. lista pra um dropdown usada em `New` e `Edit`) → `types.ts` no nível do segmento, sem prefixo de página. Achado real numa revisão: o mesmo formato de dado (`token` do reset de senha, admin sendo editado, lista de papéis, permissão) estava redeclarado em 2 a 4 arquivos diferentes da mesma página, em `Admin/Password`, `Admin/Admins` e `Admin/Roles`.
  - **Campo de texto/senha/e-mail/código ligado via `register()` usa o componente `FormField` (`components/shared/form-field/`, `docs/adr/0026`)** — nunca o trio `Label`+`Input`+`FieldError` escrito à mão de novo. `Select`/`Controller`, grupo de `Checkbox`/`fieldset` e qualquer controle que não seja `register()` direto continuam explícitos (não force esses casos dentro do `FormField` — decisão deliberada contra virar um sistema de formulário genérico orientado por configuração, ver "Consequências" do ADR).
  - **Qualquer componente (não só página) com múltiplos `useState` inter-relacionados ou lógica não-trivial (cálculo com ramificação, chamada assíncrona) extrai pra hook próprio** `use<NomeDoComponente>.ts`, ao lado do componente (`docs/adr/0029`, estende `docs/adr/0025` de página pra componente). Valor derivado simples (ex. um booleano) ou handler de 1-2 linhas continua inline — mesma exceção já prevista pra "elemento simples" (`docs/adr/0019`), não force extração que não reduz complexidade real. Achado real: `PasswordGenerator` concentrava 5 `useState` e cálculo de clamp/clipboard assíncrono direto no `.tsx` — extraído pra `usePasswordGenerator.ts`.
- **Este projeto usa React 19 — `forwardRef` nunca é usado pra expor o DOM de um componente a um `ref` externo (ex. pro `register()` do React Hook Form).** A partir do React 19, `ref` é uma prop comum do componente (incluído no tipo de prop, ex. `ref?: Ref<HTMLInputElement>`, e desestruturado/repassado como qualquer outro) — `forwardRef` está oficialmente deprecated na documentação atual do React e não deve ser usado em código novo. Gotcha real encontrado implementando `Input` (`components/shared/input/`): `forwardRef` "parecia familiar" de versões anteriores do React e funcionava sem erro nenhum, mas é padrão obsoleto — confirmado consultando a documentação atual do React (`react.dev/reference/react/forwardRef`) antes de generalizar o padrão pros outros componentes.
- **Tema escuro é via classe `.dark` na `<html>` (`@custom-variant dark`, `docs/adr/0020-dark-mode-class-strategy.md`), não `prefers-color-scheme` puro** — todo componente novo em `components/shared/` (`docs/adr/0019`) que define cor fixa (texto, borda, fundo) ganha a variante `dark:` correspondente desde a criação, nunca como retrofit depois. A classe é aplicada por um `<script>` inline em `app/views/layouts/application.html.erb` (síncrono, antes do primeiro paint, pra não ter flash de tema errado) — lógica necessariamente duplicada em `app/frontend/hooks/useTheme.ts`, já que script inline não importa módulo ES; mudar a regra de prioridade (`localStorage` vs. preferência do sistema) exige atualizar os dois lugares.
- **Nunca escreva uma tag ERB de saída (`<%= ... %>`) dentro do texto de um comentário ERB (`<%# ... %>`), mesmo como exemplo ilustrativo.** O ERB fecha o comentário no primeiro `%>` que encontrar — inclusive o de uma tag aninhada — e trata o resto do texto do comentário como HTML de saída normal a partir dali, derramando prosa crua na página renderizada. Bug real encontrado num teste manual no browser (nunca pego pelos specs de request, que não fazem parse de HTML/JS como um navegador real): o comentário do `<script>` de tema em `app/views/layouts/application.html.erb` citava `<html lang="<%= I18n.locale %>">` como exemplo dentro do próprio comentário — o texto derramado incluía a palavra `<script>` solta, que o navegador interpretava como abertura real de uma tag, fundindo o resto do comentário com o `<script>` de tema legítimo logo abaixo num único bloco JS inválido (erro de sintaxe no console, tema escuro silenciosamente sem efeito no primeiro paint). Ver `docs/bugs/code-structure.md`.
- **Hook verdadeiramente global (não amarrado a uma página) vai em `app/frontend/hooks/`** — categoria distinta do hook de formulário por página (`use<Página>Form.ts`, ao lado da página, `docs/adr/0019`). `useTheme.ts` é o primeiro exemplo: usa `useSyncExternalStore` com estado em module-level em vez de Context/Provider, porque embrulhar a árvore inteira num Provider exigiria reescrever o `setup` do `createInertiaApp`, hoje automático via `@inertiajs/vite`.
- **Dado de bootstrap exigido em todo ambiente (ex. um registro que uma associação `belongs_to` obrigatória depende de existir) vai em `db/seeds.rb`, idempotente (`find_or_create_by!`), nunca só dentro do código de uma migration.** `db:schema:load`/`db:setup` (o caminho normal pra bootstrapar qualquer ambiente novo — CI, clone local, primeiro deploy) carrega o schema direto, sem reexecutar o histórico de migrations — um dado criado só na migration nunca existiria nesse caminho. Bug real encontrado na role `owner` do RBAC (`docs/adr/0021`): a migration que criava o backfill funcionava num banco já migrado, mas um banco novo via `db:schema:load` nunca teria a role, quebrando `bin/rails admin:create` sempre. A migration pode (e deve, se fizer backfill de dado pré-existente) continuar criando o mesmo registro, mas `db/seeds.rb` é quem garante que ele existe em qualquer ambiente, independente de como o schema chegou até ali.
- **Coluna `:string` do PostgreSQL não tem limite de tamanho por padrão** (diferente de `varchar` do MySQL) — sem `validates ..., length: { maximum: N }` explícito no model, o campo aceita qualquer tamanho, inclusive payloads multi-megabyte (vetor de esgotamento de recurso). Todo atributo de input de usuário (e-mail, nome, etc.) precisa de um limite de tamanho explícito e com motivo documentado (ex. RFC 5321 pra e-mail: 254 caracteres) — bug real encontrado no model `Admin`, corrigido depois da feature já estar em uso.

## Segurança

Segurança é baseline obrigatório, não aspiração, guiado pelo [OWASP Top 10](https://owasp.org/Top10/) (ver `docs/adr/0010-security-practices-as-baseline.md` para o racional completo):

- **Validação sempre no servidor.** Validação de formulário no frontend (Zod) é UX — a autoridade final é o backend (validações do ActiveRecord + strong parameters). Nunca confie só na validação do cliente.
- **Dado que cruza fronteira de confiança é validado em runtime, não só tipado em compile-time.** Resposta de API externa, payload de formulário, webhook — valide com Zod e infira o tipo TypeScript do schema (`z.infer`), nunca deixe tipo e validação divergirem.
- **Query sempre parametrizada** — nunca interpolar valor vindo de usuário em SQL cru; use os métodos do ActiveRecord.
- **Strong parameters sempre explícito** — nunca `permit!`; liste os campos esperados.
- **Autorização não é autenticação.** Toda ação que acessa um recurso verifica que o usuário atual tem permissão sobre *aquele* recurso específico — nunca confie em `params[:id]` sozinho.
- **CSRF e escaping automático (Rails/React) nunca são desligados** sem um ADR justificando o porquê.
- **Dado sensível é criptografado em repouso** — `encrypts` (Active Record Encryption nativo do Rails) para PII sensível, não só senha.
- **Senha nunca em texto puro nem criptografia reversível** — sempre hash (`has_secure_password`/bcrypt).
- **Qualquer geração de valor aleatório sensível (senha, token) usa uma fonte criptograficamente segura — nunca `Math.random()` no frontend** (`crypto.getRandomValues`) **nem `rand`/`Random` puro no backend** (`SecureRandom`). `Math.random()`/`Random` não são adequados pra nada sensível — são previsíveis o suficiente pra um atacante reconstruir a sequência. Ver `app/frontend/lib/generatePassword.ts` (gerador de senha do painel) como referência.
- **Dado de pagamento nunca é armazenado pelo nosso banco** — sempre via token de um gateway de pagamento (nunca número de cartão, CVV, etc. tocando nosso banco).
- **Segredo nunca commitado** — Rails credentials (`master.key` fora do git) ou variável de ambiente, nunca hardcoded.
- **Log nunca expõe dado sensível** — estenda `config.filter_parameters` sempre que um novo campo sensível entrar no domínio (já cobre senha/e-mail/token/etc. por padrão).

`brakeman` e `bundler-audit` (CI) pegam sintomas automaticamente (SQLi, XSS, dependência vulnerável) — essas regras evitam a causa, não substituem a ferramenta.

## Testes

Todos os tipos de teste são esperados: unitário, integração, system/feature e, eventualmente, e2e. **Teste verde não é o critério de sucesso** — a asserção precisa de fato verificar o comportamento certo (edge cases incluídos), não só "passar". PRs com testes que não falhariam numa regressão real podem ser solicitados a melhorar a cobertura antes do merge.

- Backend: RSpec (unit + request specs) + Capybara/Cuprite (system specs, Chromium headless real via CDP). **System spec pode apresentar timeout intermitente quando rodado junto com a suíte completa** (ex. via hook `pre-push`), mesmo passando normalmente quando executado isolado — observado em `spec/system/inertia_example_spec.rb` (marcado com `FIXME`, causa raiz ainda não identificada). Se um system spec novo falhar de forma parecida, confirme rodando ele isolado antes de assumir que é uma regressão real introduzida pela sua mudança.
- **Ao testar uma rake task que chama `exit`/`abort`, qualquer `it` que não espere isso explicitamente (`expect { }.to raise_error(...)`) derruba o processo inteiro do RSpec, não só aquele exemplo** — `SystemExit`/`Exception` não é resgatado pelo runner por padrão, só `StandardError` (bug real já encontrado neste projeto). Specs `type: :task` já stubam `Kernel#exit` pra levantar `RakeTaskExited` (`spec/support/rake.rb`) em vez do `SystemExit` real — qualquer rake task nova que chame `exit` já está coberta por esse stub, não precisa reinventar.
- Frontend: Vitest + React Testing Library (componentes). **Nunca coloque `*.test.tsx` dentro de `app/frontend/pages/`** — o plugin `@inertiajs/vite` trata qualquer `.tsx` ali como página e o teste vaza pro build de produção (bug real já encontrado e corrigido neste projeto). Testes de página ficam em `app/frontend/test/pages/<mesmo-caminho>/`, importando o componente via alias `@/pages/...`.
  - **`@testing-library/react` limpa o DOM entre exemplos via `afterEach(() => cleanup())`, já configurado globalmente em `app/frontend/test/setup.ts`** — sem isso (a detecção automática da lib não ativa porque `test.globals` não está ligado no `vite.config.ts`), um `describe` com múltiplos `render()` acumula elemento de execução anterior no DOM, causando falso positivo/negativo (bug real já encontrado e corrigido). Não remova esse `afterEach` do setup global.
  - **`vi.mock("módulo", () => ({ foo: minhaVarExterna }))` quebra com `ReferenceError: Cannot access 'minhaVarExterna' before initialization`** se `minhaVarExterna` for um `const` declarado normalmente acima — o Vitest hoista o `vi.mock` pro topo do arquivo, antes da declaração rodar (bug real já encontrado escrevendo os specs das páginas do admin). Declare a mock function com `vi.hoisted`: `const { minhaVarExterna } = vi.hoisted(() => ({ minhaVarExterna: vi.fn() }))`.
  - **`userEvent.setup()` substitui `navigator.clipboard` pelo stub próprio dele por padrão (`writeToClipboard: true` nesse modo)** — qualquer `Object.defineProperty(navigator, "clipboard", ...)` feito *antes* do `setup()` é sobrescrito, fazendo um mock de `writeText` parecer nunca ter sido chamado mesmo com o código sob teste rodando certinho (gotcha real encontrado testando o gerador de senha, `PasswordGenerator`). Defina o mock de clipboard *depois* de `const user = userEvent.setup(...)`, ou passe `userEvent.setup({ writeToClipboard: false })` pra desligar o stub automático e usar só o seu.
  - **`eslint-plugin-react`'s `react/prop-types` confunde qualquer variável local chamada `props` com as props do próprio componente**, mesmo quando vem de outro lugar (ex. `const { props } = usePage()`) — gera `'x' is missing in props validation` apontando pra uma propriedade de um objeto que não tem nada a ver com as props do componente (gotcha real encontrado cabeando `usePage().props` no `PanelLayout`). Renomeie a desestruturação (ex. `const { props: pageProps } = usePage()`) em vez de investigar validação de prop que não existe.
- **Token gerado por `generates_token_for`/`has_secure_password` (ex. `admin.password_reset_token`) é diferente a cada chamada**, mesmo pro mesmo registro — embute um timestamp no payload assinado. Gotcha real encontrado escrevendo o spec do `PasswordsMailer`: comparar `mail.body` contra uma nova chamada de `admin.password_reset_token` nunca bate, mesmo com o fluxo correto (teste ficaria sempre vermelho ou passaria por sorte, não por verificar o comportamento certo). Pra testar um e-mail/link que contém um desses tokens, extraia o token de verdade do corpo renderizado (regex) e confirme que ele resolve pro registro certo (`Admin.find_by_password_reset_token(token)`), nunca compare strings de token geradas em momentos diferentes.
- **Código TOTP (`ROTP::TOTP#now`) é o mesmo durante toda a janela de 30s** — chamar de novo logo em seguida (ex. depois de já ter usado esse código em outra etapa do mesmo teste, como confirmar a ativação do 2FA) retorna **o código idêntico**, que a proteção contra replay (`AdminAuthentication::VerifyTwoFactorCode`) rejeita de propósito. Gotcha real encontrado escrevendo os specs de login com 2FA: um teste que confirma a ativação do 2FA e depois tenta logar com um código "novo" gerado na sequência falha, porque os dois códigos são o mesmo valor dentro da mesma janela — não é bug da proteção contra replay, é o teste gerando um código que já foi usado. Use `travel_to 31.seconds.from_now` entre as duas etapas pra garantir uma janela de tempo nova.
- **`config/environments/test.rb` usa `config.cache_store = :null_store`** — qualquer código que dependa de `Rails.cache` (incluindo `rack-attack`, que usa `Rails.cache` por padrão pra guardar contador de throttle) vira um no-op silencioso nesse ambiente: um teste de rate limit passaria mesmo que o throttle fosse removido do código, sem nenhum teste ficar vermelho. Achado real ao testar o rate limiting do login (`rack-attack`) — `spec/support/rack_attack.rb` troca `Rack::Attack.cache.store` por um `ActiveSupport::Cache::MemoryStore` novo em cada request spec, garantindo throttle de verdade. Qualquer teste futuro que dependa de `Rails.cache` (não só `rack-attack`) precisa do mesmo cuidado — verifique isso quebrando a lógica de propósito antes de confiar que o teste pegaria a regressão.
- **`allow(objeto.attachment_name).to receive(:content_type)` (ou outro método delegado) falha com `"does not implement: content_type"` pra um `has_one_attached`/`has_many_attached`** — `ActiveStorage::Attached::One`/`Many` delega esses métodos ao blob por `method_missing`, e a verificação de dublê parcial do RSpec (`allow(...).to receive(...)` sobre um objeto real, não um dublê puro) exige o método existir de fato na classe, não só responder via `method_missing`. Gotcha real encontrado testando a validação de tamanho do `logo` em `StoreSetting`: em vez de mockar, anexe um arquivo real que já viola a regra (ex. um `StringIO` gerado em memória maior que o limite, sem precisar de um binário de verdade commitado) e deixe a validação rodar sobre o attachment de fato.
- **Spec de auditoria (PaperTrail) que checa `change_reason` sem checar `whodunnit` só prova a metade do que importa.** `change_reason` prova o "por quê"; `whodunnit` prova o "quem" — e nenhum spec do projeto checava `whodunnit` até ser notado numa revisão deliberada de cobertura de auditoria (`spec/requests/admin/admins_spec.rb`/`spec/requests/admin/roles_spec.rb`), mesmo sendo exatamente o tipo de regressão silenciosa que um mecanismo central (`BaseController#user_for_paper_trail`) quebrando afetaria de uma vez só, sem nenhum teste pra avisar. Todo spec de request que afirma "registra versão no PaperTrail" precisa verificar `version.whodunnit` (geralmente `eq(admin.id.to_s)`), não só `version.change_reason`.
- E2e: **Playwright** (não Cypress — melhor suporte a TypeScript, multi-browser nativo e não compete com o Vitest como test runner). Entra quando houver fluxo de UI real para testar — não antes.
- Markdown: todo `.md` do repositório segue o `.markdownlint.json` da raiz. **Documento que repete subtítulos por seção** (ex. cada bug em `docs/bugs/<categoria>.md` tem seu próprio `### Causa raiz`, `### Impacto`, etc.) **precisa da opção `MD024` com `siblings_only: true`** — sem isso, o markdownlint sinaliza falso positivo de "heading duplicado" em qualquer arquivo com 2+ entradas seguindo o mesmo template (bug real encontrado implementando `docs/bugs/`). Com `siblings_only`, só heading repetido sob o mesmo heading-pai é sinalizado.

PRs precisam incluir testes para o comportamento novo/alterado, e a suíte completa precisa passar:

```bash
bundle exec rspec                # testes backend
pnpm test                        # testes frontend (Vitest)
pnpm dlx playwright test         # testes e2e (quando existirem)
pnpm lint                        # lint JS/TS (ESLint)
pnpm format:check                # formatação JS/TS (Prettier)
bundle exec rubocop              # lint Ruby
bundle exec brakeman             # análise de segurança
pnpm dlx markdownlint-cli2 "**/*.md"  # lint de markdown
```

## Processo de PR

0. `pnpm install` já ativa os git hooks do projeto (Husky — ver seção "Git hooks" abaixo); nenhum passo manual.
1. Fork do repositório, **um branch por mudança** a partir de `main` — não misture várias mudanças não relacionadas no mesmo branch. Nome do branch segue um padrão fixo, ver "Padrão de nome de branch" abaixo.
2. Commits em português, no padrão **Commitizen/Conventional Commits** (`tipo: descrição` — tipo em inglês por convenção da ferramenta: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `style`, `perf`, `build`, `ci`, `revert`; descrição/corpo em português), bem detalhados sobre tudo que foi feito e por quê — nunca mensagens genéricas como "ajustes" ou "fix".
3. **Sempre abra um PR** (nunca commit direto na `main`), com descrição **detalhada o suficiente pra uma revisão de código de verdade** — não um resumo genérico. Liste os arquivos relevantes tocados e o porquê, qualquer decisão tomada durante a implementação que não estava no escopo original (ex. um bug encontrado e corrigido no caminho), e o resultado das verificações locais (lint/teste/build). Linke a issue relacionada se houver.
4. **PRs pequenos e focados** — um PR resolve uma coisa. Se a mudança crescer e passar a resolver várias coisas não relacionadas, quebre em PRs menores.
5. **Revise seu próprio diff antes de abrir o PR** — releia as mudanças, rode lint/testes relevantes localmente, confira que nada ficou pela metade. Não abra PR só na esperança de que o CI pegue os problemas.
6. CI (lint, segurança, testes) precisa passar antes do review.
7. Se o PR formalizar uma decisão de arquitetura/produto nova (não só implementação de algo já decidido), inclua o ADR correspondente no mesmo PR — ver `docs/adr/0001-record-architecture-decisions.md` e a skill `create-adr`.
8. **Referencie um PR em qualquer comentário de código, ADR ou documentação sempre pelo número real (`#NN`, o que o GitHub atribui ao abrir o PR), nunca por um codinome/letra informal** (ex. "PR K", "PR J") usado só durante o planejamento. Um codinome não aparece em nenhum lugar público do projeto (título do PR, branch, commit) e não significa nada pra quem lê o código depois — vira referência órfã. Enquanto o PR ainda não tem número (durante a própria implementação), não cite nenhum identificador: descreva a decisão em termos do projeto, sem precisar apontar pra qual PR a introduziu.

### Git hooks

Husky gerencia os hooks de git, ativados automaticamente por `pnpm install` (script `prepare` do `package.json`) — sem passo manual.

- **`pre-commit`** (`.husky/pre-commit`): roda [lint-staged](https://github.com/lint-staged/lint-staged) (`lint-staged.config.mjs`) — ESLint + Prettier nos arquivos `.ts`/`.tsx`/`.js`/`.jsx` staged, Prettier em `.json`/`.css`/`.yml`/`.yaml`, Rubocop (`-a`, autocorreção segura) em `.rb`. Só toca o que está staged, rápido por natureza.
- **`commit-msg`** (`.husky/commit-msg`): roda [commitlint](https://commitlint.js.org/) (`commitlint.config.mjs`, estende `@commitlint/config-conventional`) validando o padrão Conventional Commits do passo 2 acima, e em seguida o bloqueio de atribuição de IA (ver "Sem atribuição de IA" abaixo).
- **`pre-push`** (`.husky/pre-push`): roda a suíte completa (`bundle exec rspec` e `pnpm test`) — intencionalmente mais pesado que o pre-commit, só roda ao empurrar pra um remoto, não a cada commit local.

### Padrão de nome de branch

```text
<tipo>/<descricao-curta-em-ingles>
```

- **`<tipo>`**: exatamente o mesmo vocabulário dos commits — `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `style`, `perf`, `build`, `ci`, `revert`.
- **`<descricao-curta-em-ingles>`**: kebab-case, sempre em inglês (mesmo o resto do projeto sendo em português — igual ao nome de arquivo de ADR), curta e descritiva do que a branch faz, não do ticket/issue.
- Exemplos: `feat/coupon-discount-calculator`, `fix/digital-access-release-bug`, `docs/environment-setup-runbook`, `chore/enable-docker-wsl-integration`, `refactor/checkout-service-extraction`.
- Nunca um nome genérico (`fix/bug`, `feat/updates`) nem baseado só em número de issue sem descrição.

## Sem atribuição de IA

Nunca inclua qualquer atribuição de autoria de IA (`Co-Authored-By: Claude`, "Generated with Claude Code", `noreply@anthropic.com` ou equivalente) em commits, PRs ou qualquer artefato deste repositório — mesmo que a ferramenta usada para contribuir tenha gerado essa linha por padrão, remova-a antes de commitar. Isso é bloqueado tecnicamente em duas camadas:

- **Hook local** (`.husky/commit-msg`): rejeita o commit antes mesmo de ser criado. Ativado automaticamente por `pnpm install` (ver "Git hooks" acima).
- **CI** (`.github/workflows/no-ai-attribution.yml`): verifica commits e o corpo/título do PR, como segunda camada de proteção caso o hook local seja ignorado ou não esteja ativado.

**Isso não significa que IA não possa ser usada no desenvolvimento.** Pode, e este projeto é construído com auxílio de IA — a única exigência é que ela nunca apareça como colaboradora/co-autora no repositório (questão de organização/estética, não uma restrição sobre a ferramenta usada). Código produzido com ou sem auxílio de IA passa pelos mesmos padrões deste documento, sem exceção: Clean Code/Clean Architecture/SOLID, nomes descritivos, sem string mágica, HTML semântico, testes de verdade, lint e segurança limpos.
