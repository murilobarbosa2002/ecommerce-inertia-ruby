# Convenções de frontend (React/TypeScript)

Ver [`code-style-and-architecture.md`](code-style-and-architecture.md) para convenções gerais e [`../../CONTRIBUTING.md`](../../CONTRIBUTING.md) para o índice completo.

- TypeScript, componentes React pequenos e testáveis. Siga ESLint (`pnpm lint`) e Prettier (`pnpm format:check`) configurados no projeto — `eslint.config.mjs` inclui regras de tipagem estrita (typescript-eslint `strictTypeChecked`), React, acessibilidade (`jsx-a11y` strict) e Tailwind; Prettier (com `prettier-plugin-tailwindcss`) é quem formata/ordena classes, não o ESLint.
- **No frontend, a regra geral de comentário (ver `code-style-and-architecture.md`) tem um recorte mais estrito pra arquivo de página/componente de apresentação (`app/frontend/pages/**/*.tsx`, `app/frontend/components/**/*.tsx`): zero comentário, nem mesmo o "porquê não óbvio" que o resto do projeto permite.** A explicação de uma decisão não trivial que nasceria num comentário desses vai pra um dos lugares que já existem pra isso: `docs/contributing/` (convenção que generaliza), `docs/bugs/<categoria>.md` (bug real encontrado) ou um ADR (decisão de arquitetura/produto) — nunca embutida no `.tsx`. **Arquivo de hook (`useAlgumaCoisa.ts`) e arquivo de tipagem (`*.types.ts`) continuam podendo ter comentário "porquê não óbvio", igual a qualquer outro código** — só componente/página de apresentação é que fica sem. Duas exceções deliberadas, tratadas como hook mesmo sendo `.tsx`: `app/frontend/components/motion/*.tsx` (primitivos de animação — `Reveal`, `StaggerGroup`, etc. — cujo "porquê" de cada prop/cálculo de easing não é óbvio e não tem outro lugar natural pra viver) e `*.variants.ts` (definição de variante `tv()`, mesmo racional).
- **Formulário sempre com Zod + `zodResolver` + React Hook Form**, nunca validação manual ad-hoc. **Componente de UI com comportamento (modal, select, checkbox, etc.) sempre parte de um primitivo do pacote `radix-ui`**, estilizado por este projeto com Tailwind — nunca reimplementado do zero, nunca vindo de outra lib headless (exceção pontual e documentada: `react-day-picker` pro calendário/seletor de data, já que Radix UI não tem nenhum primitivo equivalente — `docs/adr/0035`). **Variante de estilo usa `tv()` do `tailwind-variants`**, não concatenação manual de classe condicional. Racional completo em `docs/adr/0012-form-validation-and-ui-primitives-stack.md`.
  - **Todo campo de formulário bindado a um componente Radix controlado (`Select`, etc.) via `Controller` precisa de valor inicial definido em `defaultValues` do `useForm()`** — mesmo sendo string vazia, nunca `undefined`. Sem isso, o componente nasce "uncontrolled" e vira "controlled" assim que o primeiro valor real é escolhido, gerando o aviso real do React de componente trocando de modo no meio da vida (gotcha real encontrado integrando `Select` com RHF no formulário de admins).
  - **Elemento condicionalmente envolto por um primitivo Radix com abrir/fechar próprio (`Tooltip`, `Popover`, etc.) nunca alterna entre "com wrapper" e "sem wrapper" via ternário de tipo** (ex. `collapsed ? <Tooltip>{x}</Tooltip> : x`) — isso faz o `Root`/`Trigger` do Radix desmontar e remontar a cada troca de estado; se estiver aberto (hover) no momento da troca, o unmount abrupto interrompe o fechamento controlado do Radix e o `Portal`/`Content` fica preso na tela. Gotcha real encontrado no botão de recolher/expandir a sidebar e no `SidebarItem` recolhido (`docs/bugs/code-structure.md`): manter o trigger sempre montado dentro do mesmo `Tooltip`, condicionando só se o `Content` é renderizado (`content` falsy ⇒ sem `Portal`/`Content`, `Root`/`Trigger` intactos), resolve — o Radix volta a controlar o fechamento normalmente. Atenção: mesmo com o trigger sempre montado, o rastreamento de hover do `Root` roda independente de o `Content` existir — se `open` não for controlado e filtrado por "há conteúdo pra mostrar", um hover que começa sem conteúdo pode reabrir o tooltip sozinho, sem novo hover, quando o conteúdo volta a existir (mesmo gotcha, ver `Tooltip.tsx`).
  - **Ao definir `overflow-x`/`overflow-y` com Tailwind (`overflow-x-*`/`overflow-y-*`), sempre declare os dois eixos, nunca só um.** A spec de overflow do CSS não permite a combinação "um eixo `auto`/`scroll`, outro no valor inicial `visible`" — o navegador força o eixo `visible` a computar como `auto` também, pra não deixar conteúdo escapar sem controle. Isso pode desenhar uma barra de rolagem nativa num eixo em que nenhuma classe pediu isso, sempre que o conteúdo momentaneamente ultrapassar o container nesse eixo (ex. durante uma transição CSS de largura/altura). Gotcha real encontrado no `<nav>` da sidebar (`overflow-y-auto` sozinho, `docs/bugs/code-structure.md`): bastava a largura do menu estar em transição e o rótulo de um item já visível pra o `overflow-x` computado virar `auto` e desenhar a barra horizontal por um instante — corrigido declarando `overflow-x-hidden` explícito.
- **Nunca usar o tipo `any`.** Toda variável, parâmetro, retorno de função e prop de componente precisa de um tipo real. Se o tipo correto não for óbvio, pesquise (documentação oficial da lib, Context7) em vez de recorrer a `any` ou `as any` como atalho. `unknown` + narrowing é aceitável quando o tipo genuinamente não pode ser conhecido antecipadamente (ex. parsing de JSON externo) — `any` nunca é.
- **`router.reload`/`router.get` do Inertia, com array vazio em `data`, nunca chega como array vazio nos `params` do Rails numa requisição GET.** A serialização de query string (lib `qs`) descarta por padrão qualquer chave cujo valor seja um array vazio — a chave simplesmente não aparece na URL, indistinguível de "nunca enviada". Pra um filtro onde "nada selecionado" precisa ser diferente de "nenhum filtro aplicado ainda", envie uma string (ex. `selected.join(",")`) em vez de array — uma string vazia ainda chega normalmente (`chave=`). No controller, distinga com `params.key?(:chave)` (ausente vs. presente-e-vazio), nunca só `Array(params[:chave]).presence`. Gotcha real encontrado no filtro de tipo de evento do dashboard (`docs/bugs/testing-and-tooling.md`).
- **Mensagem de flash do Inertia é lida via `usePage().flash`, nunca `usePage().props.flash`.** `flash` é um campo próprio do objeto de página (`{ component, props, flash, ... }`), paralelo a `props`, não aninhado dentro dele — bug real encontrado testando no browser (`usePage().props.flash` sempre retornava `undefined`, quebrando a página inteira). Só existe de fato quando há `notice:`/`alert:` pra mostrar; trate como opcional (`flash?.notice`), mesmo o tipo de `@inertiajs/core` declarando como sempre presente.
  - **Todo layout de página (`AuthLayout`, `PanelLayout`, qualquer um novo) renderiza `Banner`/`Toast` a partir de `usePage().flash` desde a criação** — nunca como retrofit depois que uma página já precisa mostrar erro/sucesso. Controller sinaliza falha de validação via `redirect_to ..., alert: ...` (mensagem localizada, ex. `admin.errors.full_messages.to_sentence`), nunca via `inertia: { errors: ... }` (protocolo de erro por campo do Inertia) — nenhum componente deste projeto consome `usePage().props.errors`/chama `setError` do React Hook Form com ele; gotcha real encontrado implementando `AdminsController`, onde os dois problemas (controller usando um protocolo sem consumidor, `PanelLayout` sem feedback nenhum) deixavam qualquer mensagem de erro/sucesso invisível.
- **Fonte do projeto é Inter, self-hosted via `@fontsource-variable/inter`** (`app/frontend/entrypoints/application.css`, `--font-sans` do `@theme`) — nunca depender só do stack padrão de fontes do sistema operacional (`-apple-system`, `Segoe UI`, etc.). Bug real encontrado testando no browser: sem nenhuma dessas fontes instalada na máquina, o fallback do Chromium renderizava espaçamento entre palavras visivelmente quebrado, sem nenhuma propriedade CSS indicando a causa.
- **URL/ação de formulário no frontend nunca é string hardcoded** (`href="/admin/login"`, `router.post("/admin/login", data)`) — use os helpers tipados gerados por `js-routes` a partir de `config/routes.rb`, importados de `@/routes` (ex. `admin_session_path()`, `new_admin_password_path()`), mesmo nome do helper Ruby correspondente (`docs/adr/0018-js-routes-typed-path-helpers.md`). Rota renomeada/removida quebra em compile-time (`pnpm check`) em todo call site, não em runtime no browser — bug real quase causado no PR das primeiras páginas de autenticação, só pego por revisão manual. `app/frontend/routes.js`/`routes.d.ts` são gerados (gitignorados, fora do escopo do ESLint), nunca editados à mão.
- **Hierarquia fixa de componente/arquivo no frontend** (`docs/adr/0019-frontend-component-hierarchy-and-file-organization.md`):
  - **Primitivo de UI reutilizável** (usado por mais de uma página) vira componente em `components/shared/<nome-do-componente>/` (kebab-case, uma pasta por componente — nunca agrupado por categoria genérica como `form/`), com três arquivos de responsabilidade única dentro: `<Nome>.types.ts` (tipo/`interface` de prop), `<Nome>.variants.ts` (variante `tv()`), `<Nome>.tsx` (só o JSX do componente, importando os outros dois). Um primitivo nunca fica aninhado dentro da pasta de outro só por coincidência de uso atual (ex. `label/`/`field-error/` não ficam dentro de `input/` mesmo só aparecendo ao lado de `Input` até agora) — a pasta reflete se o componente é genérico por natureza, não quantos lugares o usam hoje. **Exceção justificada: ícone SVG estático vive em `components/shared/icons/<nome-do-ícone>/`** (`docs/adr/0027`) — diferente de `form/` (papéis diferentes agrupados por coincidência), ícone é genuinamente a mesma categoria de coisa (SVG estático sem variante nem prop própria), já reconhecida como tal na exceção de "sem variante/sem prop" deste mesmo ADR. **Ícone novo da interface vem do `lucide-react`**, importado direto no ponto de uso (`docs/adr/0032`), decorativo com `aria-hidden="true"`; `icons/` fica só pra SVG próprio que o lucide não oferece. **Parte de componente composto** (ex. `CardHeader`/`CardBody`/`CardFooter` de `Card`), que não tem uso fora do pai, vive em `components/shared/<pai>/<parte>/` com os mesmos três arquivos (`docs/adr/0033`). **Item de menu do painel é uma entrada em `app/frontend/config/adminNavigation.ts`** (rota, ícone, rótulo de I18n e a permissão exigida) — nunca um link escrito direto no layout; filtro por permissão e item ativo vivem em `lib/navigation/` (`docs/adr/0034`). Navegação interna do painel usa o `Link` do `@inertiajs/react` (sem recarregar a página), e todo teste que renderiza o `PanelLayout` mocka `Link` (`Link: "a"`).
  - **Componente específico de uma página** (não reutilizável fora dela, ex. o `<form>` inteiro de uma tela) vive em `pages/<Segmento>/components/<Página>Form.tsx` — pasta `components/` local ao segmento, nunca confundida com `components/shared/` (genérico) ou `components/admin/` (variante de estilo sem componente próprio ainda).
  - **Arquivo da página (`New.tsx`, `Edit.tsx`) só compõe o layout** — `useTranslation`, `<AuthLayout>`/`<Head>`, e o(s) componente(s) filho(s). Nenhum `useForm`, schema, `<form>` inteiro ou `router.post`/`router.patch` direto nesse arquivo. **Isso vale pra qualquer hook/lógica de interação, não só formulário** (`docs/adr/0025`) — uma ação com `usePage()`, condição de permissão ou efeito colateral (ex. confirmar e enviar uma requisição) vira seu próprio componente em `components/`, nunca inline na página. Achado real: o botão "Resetar 2FA" (`Admin/Admins/Edit.tsx`, #54) nasceu direto na página, chamando `usePage()` e resolvendo a lógica de confirmação ali mesmo — corrigido extraindo pra `components/ResetTwoFactorButton.tsx`.
  - **Schema, hook e componente de formulário, cada um no seu arquivo**: `<Página>.schema.ts` (Zod + tipo derivado), `use<Página>Form.ts` (encapsula `useForm`/`zodResolver`/submissão, ao lado do arquivo da página, fora de `components/` — é lógica, não apresentação) e `pages/<Segmento>/components/<Página>Form.tsx` (o JSX do formulário, chamando o hook).
  - **Tipo da entidade recebida como prop do backend (distinto do tipo derivado do schema Zod) sempre em arquivo próprio, nunca inline/duplicado entre página/hook/componente** (`docs/adr/0025`): usado só por uma página → `<Página>.types.ts`, sempre com o formato **completo** das props da página (não só a entidade — form component que recebe exatamente o mesmo formato reusa o mesmo tipo, nunca redeclara); usado por mais de uma página do mesmo segmento (ex. lista pra um dropdown usada em `New` e `Edit`) → `types.ts` no nível do segmento, sem prefixo de página. Achado real numa revisão: o mesmo formato de dado (`token` do reset de senha, admin sendo editado, lista de papéis, permissão) estava redeclarado em 2 a 4 arquivos diferentes da mesma página, em `Admin/Password`, `Admin/Admins` e `Admin/Roles`.
  - **Campo de texto/senha/e-mail/código ligado via `register()` usa o componente `FormField` (`components/shared/form-field/`, `docs/adr/0026`)** — nunca o trio `Label`+`Input`+`FieldError` escrito à mão de novo. `Select`/`Controller`, grupo de `Checkbox`/`fieldset` e qualquer controle que não seja `register()` direto continuam explícitos (não force esses casos dentro do `FormField` — decisão deliberada contra virar um sistema de formulário genérico orientado por configuração, ver "Consequências" do ADR).
  - **Qualquer componente (não só página) com múltiplos `useState` inter-relacionados ou lógica não-trivial (cálculo com ramificação, chamada assíncrona) extrai pra hook próprio** `use<NomeDoComponente>.ts`, ao lado do componente (`docs/adr/0029`, estende `docs/adr/0025` de página pra componente). Valor derivado simples (ex. um booleano) ou handler de 1-2 linhas continua inline — mesma exceção já prevista pra "elemento simples" (`docs/adr/0019`), não force extração que não reduz complexidade real. Achado real: `PasswordGenerator` concentrava 5 `useState` e cálculo de clamp/clipboard assíncrono direto no `.tsx` — extraído pra `usePasswordGenerator.ts`.
  - **Hook verdadeiramente global (não amarrado a uma página) vai em `app/frontend/hooks/`** — categoria distinta do hook de formulário por página (`use<Página>Form.ts`, ao lado da página). `useTheme.ts` é o primeiro exemplo: usa `useSyncExternalStore` com estado em module-level em vez de Context/Provider, porque embrulhar a árvore inteira num Provider exigiria reescrever o `setup` do `createInertiaApp`, hoje automático via `@inertiajs/vite`.
- **Este projeto usa React 19 — `forwardRef` nunca é usado pra expor o DOM de um componente a um `ref` externo (ex. pro `register()` do React Hook Form).** A partir do React 19, `ref` é uma prop comum do componente (incluído no tipo de prop, ex. `ref?: Ref<HTMLInputElement>`, e desestruturado/repassado como qualquer outro) — `forwardRef` está oficialmente deprecated na documentação atual do React e não deve ser usado em código novo. Gotcha real encontrado implementando `Input` (`components/shared/input/`): `forwardRef` "parecia familiar" de versões anteriores do React e funcionava sem erro nenhum, mas é padrão obsoleto — confirmado consultando a documentação atual do React (`react.dev/reference/react/forwardRef`) antes de generalizar o padrão pros outros componentes.
- **`eslint-plugin-react-hooks` deste projeto proíbe chamar `setState` dentro do corpo de um `useEffect`, e ler ou escrever `ref.current` durante o render** (`react-hooks/set-state-in-effect`, `react-hooks/refs`) — regras mais estritas que o padrão oficial do React, pensadas pro React Compiler. Pra "refletir uma prop que muda em estado local" (ex. mostrar um toast quando `usePage().flash` muda), não use `useEffect(() => setState(prop), [prop])`: compare o valor atual com o último visto (guardado em outro `useState`, nunca em `useRef`) direto no corpo do componente, e ajuste o estado condicionalmente ali — é o padrão oficialmente endossado pra esse caso ("adjusting state when a prop changes", não é sincronizar com sistema externo). Pra um recurso de verdade externo ao React (ex. revogar uma `URL.createObjectURL` quando o valor que a gerou muda ou o componente desmonta), crie a URL no handler que a precisa e deixe o `useEffect` só fazer a limpeza (`return () => revoke(...)`, sem nenhum `setState` dentro). Gotcha real encontrado duas vezes na Fase D do painel (`PanelLayout`, pro flash virar toast; `FileDropzone`, pro preview do arquivo escolhido).
- **Tema escuro é via classe `.dark` na `<html>` (`@custom-variant dark`, `docs/adr/0020-dark-mode-class-strategy.md`), não `prefers-color-scheme` puro** — todo componente novo em `components/shared/` (`docs/adr/0019`) que define cor fixa (texto, borda, fundo) ganha a variante `dark:` correspondente desde a criação, nunca como retrofit depois — a menos que use os tokens semânticos de `app/frontend/styles/tokens.css` (`bg-surface`, `text-fg-muted`, `border-line`, `bg-accent`, ...), que já trocam sozinhos entre os temas (`docs/adr/0031`); cor nova em token exige manter o contraste mínimo, validado por `app/frontend/test/styles/tokens.test.ts`. A classe é aplicada por um `<script>` inline em `app/views/layouts/application.html.erb` (síncrono, antes do primeiro paint, pra não ter flash de tema errado) — lógica necessariamente duplicada em `app/frontend/hooks/useTheme.ts`, já que script inline não importa módulo ES; mudar a regra de prioridade (`localStorage` vs. preferência do sistema) exige atualizar os dois lugares.
